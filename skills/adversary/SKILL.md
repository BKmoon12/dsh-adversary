# 假想敌：交付物发布前的对抗性预演

## 这个技能解决什么

用户写完一份东西，准备发出去。他知道有问题，但作为作者看不见——因为他脑子里装的是自己的逻辑，对方脑子里装的是自己的关切。这两套东西不重叠的地方，就是发布后被打回来的地方。

这个技能做的事：在发出去之前，请几个人站到对方的位置上，把这份东西按对方的关切点读一遍，指出会被攻击的地方。

**定位必须记牢：这是压力测试，不是预测。** 你不掌握对方的真实想法、内部政治、历史包袱、当下的心情。你只能保证：如果对方从这个角度想，他会问什么、你会卡在哪。这个边界要主动告诉用户，不要包装成"我猜到了你领导会怎么说"。

## 触发时机

用户在以下情境里提出请求时用：

- 写完一份要交给领导的文件 / 报告 / 方案，想先过一遍
- 要给客户发方案、报价、结项材料
- 要发一条朋友圈、一条抖音、一篇公众号，担心评论区
- 要答辩、要汇报、要路演，想先被问一遍
- 明确说"帮我找找问题""假设你是甲方""领导会怎么挑"

不需要触发：用户只是让你润色文字、改格式、写内容。那是写作任务，不是预演任务。

## 流程

### 第 1 步：确认两件事，缺一件就问

1. **交付物本身**：要审查的完整文本。用户可能贴一段，也可能说"就是刚才那个"。**不要替用户概括或"理解大意"**——预演的价值在于针对原文的具体词句开火，概括过的文本挑出来的都是空话。
2. **假想敌是谁**：这份东西发给谁、谁会看、谁会挑。用户说得模糊（"就领导吧"）时，追问一句他关心什么（是结果、是钱、是合规、是面子），再定角色。

不确定该给谁看时，调用 `adversary_personas` 把角色卡列出来让用户挑。用户已经说清楚（"我们那位只关心预算的副总"）时，直接用 `customPersonas` 现建一张卡，不要为了走流程去列清单。

### 第 2 步：选角色，1–3 个

- **1 个**：只关心一个特定的人，或只想快速过一遍。
- **2–3 个**：最常用的配置。选关注点不重叠的，别选三个都盯格式的。
- **超过 3 个**：收益递减，意见开始重复，还会把注意力摊薄。用户坚持要更多时，拆成两轮跑。

**不要默认选"严厉领导 + 挑剔客户 + 杠精"。** 杠精只在交付物是公开传播内容时才值得上场；内部文件里放杠精，出来的是一堆无用的抬杠。角色要匹配交付物的真实受众。

选角色的判断：这份东西发出去，谁的否定会真的让它返工？那个人就是应该上场的角色。

### 第 3 步：调 `adversary_review`

```
adversary_review({
  deliverable: "<交付物原文，一字不改>",
  personas: ["strict-boss", "picky-client"],
  deliverableType: "文件",
  intensity: "normal"
})
```

工具返回一份任务书。里面已经写好了：每个角色的视角、关注焦点、异议风格、语气示范、四段输出格式，以及多角色时的汇总规则。**按任务书执行，不要自己另起一套格式。**

### 第 4 步：逐个扮演

按任务书的顺序，一个角色一段。每个角色四段固定输出：第一反应 / 会提出的异议 / 最可能被抓住的薄弱点 / 一条修改建议。

### 第 5 步：汇总

多角色时按任务书的规则合并：共同指向优先，合并同类，标注 P0/P1/P2。最后给"最可能被截图的一句话"和"如果只能改三处"。

## 输出规范

### 每个角色

用角色名做小标题。正文按四段走，不加开场白。

**第一反应**：一到两句话，用这个人的口吻直接说。不写"我认为这份文件存在以下问题"，写"这个我看不明白，你到底要我批什么"。第一反应是情绪和判断，不是分析。

**会提出的异议**：2–4 条。每条写成三截：

```
「原文里的具体片段」→ 他会怎么质疑 → 他为什么在意这一条
```

引号里必须是原文里真实存在的词句。做不到引原文的异议，说明它不来自这份东西，删掉。

**最可能被抓住的薄弱点**：只写一条。是这份东西在他眼里最致命的地方——不是"最严重的问题"，是"他最先发难、而且你最难答上来的那一个"。

**一条修改建议**：具体到改哪一句、改成什么方向。禁止"建议加强逻辑""建议补充数据"这类可以套在任何文件上的话。

### 汇总（多角色时）

一张表，列：优先级 / 异议 / 指向原文位置 / 提出者 / 是否共同指向。

判定共同指向：**两个及以上不同角色针对同一处原文**。同一角色说了两遍不算。措辞不同但指向同一处的，合并成一条，提出者写全部角色名。

优先级：共同指向 > 每个角色的致命薄弱点 > 其余单条。P0 不改会被打回，P1 会被追问需要准备答案，P2 可以不改但值得知道。

表后两段，各不超过三句：最可能被截图的一句话、如果只能改三处的排序。

### 收尾声明

固定附一句，不长篇大论：

> 以上是压力测试。它不代表对方真会这么说，只代表如果你被这么问，这些是要提前想好的地方。

## 铁律

1. **一次只演一个人。** 角色之间不互相引用、不补充、不总结前一个角色。串味了，多角色的意义就没了——用户要的是三个独立视角，不是一份被综合过的意见。
2. **只挑毛病，不夸。** 没有"整体不错""思路清晰，但是"这类缓冲句。第一句就落在问题上。用户不需要鼓励，需要知道哪里会漏。
3. **必须引原文。** 每条异议都要落在具体词句上。这条最容易被违反：模型很擅长产出"这份材料在数据支撑方面可能不足"这种放之四海皆准的话，它对用户毫无价值。
4. **不编造事实。** 不掌握信息时（对方的真实态度、内部人事、行业数据），把质疑写成"他会问你……"，而不是"这里数据是错的"。前者是预演，后者是造谣。
5. **不和稀泥。** 三个角色都提同一个问题，就明说这是共同指向、优先级最高，不要为了显得全面而把它们摊平。
6. **不改用户的活。** 除非用户要求，不要顺手把交付物重写一遍。预演的输出是"哪里会出问题"，不是"改好的版本"。

## 常见失误

- **角色千篇一律**：三个角色说出来的话像同一个人换了三副眼镜。原因是没吃透角色卡里的"语气示范"和"会被点什么着"。演之前先在心里过一遍这个人平时怎么说话。
- **异议全是抽象名词**：出现"逻辑闭环""颗粒度""赋能"这类词，说明没在读原文，在背模板。删掉重写。
- **第一反应写成摘要**：第一反应是"他看到第一眼时的情绪和判断"，不是内容复述。
- **汇总变成列表**：多角色时最容易偷懒——把三份清单拼在一起就当汇总了。汇总的价值在于合并和排序，不合并就没有信息增量。
- **过度承诺**：写出"领导一定会觉得这个方案不成熟"这种断言。改成"他会问你凭什么觉得这个方案现在能推"。

## 边界

- 只审查文本，不读本地文件（V1）。用户要用文件时，请他把内容贴进来。
- 不模拟真人性格细节。它演的是"这个位置上的典型关切"，不是"你座位上那个人"。用户问"像不像我们领导"时，直接说明这个区别。
- 不做评论区多人互动模拟（那是 V2 的模式 B）。用户要求"让评论区吵起来"时，说明当前版本只做静态预演，可以先用路人网友、杠精、截图传播者三张卡各自预测一遍。
